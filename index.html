配置子服务器下多个用户实例数据 01 OCC 02 fdserver 03 04 评价系统
– ============================================================
– 1. 备份表（强烈建议）
– ============================================================
SELECT * INTO dbo.SystemInfo_Backup_90300_90399 FROM dbo.SystemInfo;

– ============================================================
– 2. 设置固定起始端口（端口将从 61001 开始）
– ============================================================
DECLARE @StartPort INT = 61000; – 实际端口为 @StartPort + n，n从1开始

– ============================================================
– 3. 开启事务（便于回滚）
– ============================================================
BEGIN TRANSACTION;

– ============================================================
– 4. 生成 400 条记录（100个实例 × 4条）
– 实例号从 90300 到 90399
– ============================================================
WITH Numbers AS (
SELECT TOP 400 ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS n
FROM sys.objects a
CROSS JOIN sys.objects b – 若不够可再加 CROSS JOIN sys.objects c
)
INSERT INTO dbo.SystemInfo (
ID, SystemID, Name, Remark, McastList, Address,
RecordTime, Status, port, address_udp, port_udp,
IsKeySubSystem, 位置X0, 位置Y0, 位置X1, 位置Y1,
显示图片, InitStatus, ip, UnitNo, SystemType, SystemSubType
)
SELECT
NULL, – 假设 ID 为自增列
(90300 + (n - 1) / 4) * 100 + ((n - 1) % 4 + 1) AS SystemID,
N’服务实例:’ + CAST((90300 + (n - 1) / 4) AS NVARCHAR(10)) + N’_索引:’ + CAST(((n - 1) % 4 + 1) AS NVARCHAR(10)),
NULL, NULL, NULL, NULL, NULL,
@StartPort + n, – 端口从 61001 开始连续分配（61001, 61002, … 61400）
NULL, NULL, NULL,
NULL, NULL, NULL, NULL,
NULL, NULL,
‘10.1.12.132’,
NULL, NULL, NULL
FROM Numbers
ORDER BY n;

– ============================================================
– 5. 验证插入结果
– ============================================================
– 5.1 检查记录总数（应为 400）
SELECT COUNT(*) AS 插入条数
FROM dbo.SystemInfo
WHERE ip = ‘10.1.12.132’
AND SystemID BETWEEN 9030001 AND 9039904;

– 5.2 检查是否有重复 SystemID（应返回 0 行）
SELECT SystemID, COUNT()
FROM dbo.SystemInfo
WHERE ip = ‘10.1.12.132’
AND SystemID BETWEEN 9030001 AND 9039904
GROUP BY SystemID
HAVING COUNT() > 1;

– 5.3 检查端口是否重复（应返回 0 行）
SELECT port, COUNT()
FROM dbo.SystemInfo
WHERE ip = ‘10.1.12.132’
GROUP BY port
HAVING COUNT() > 1;

– 5.4 查看端口范围（应是从 61001 到 61400）
SELECT MIN(port) AS 最小端口, MAX(port) AS 最大端口
FROM dbo.SystemInfo
WHERE ip = ‘10.1.12.132’
AND SystemID BETWEEN 9030001 AND 9039904;

– 5.5 查看前 20 条示例数据
SELECT TOP 20 SystemID, Name, port
FROM dbo.SystemInfo
WHERE ip = ‘10.1.12.132’
AND SystemID BETWEEN 9030001 AND 9039904
ORDER BY SystemID;

– ============================================================
– 6. 如果验证无误，提交事务；否则回滚
– ============================================================
– 若一切正常，执行：
COMMIT;
– 若有异常，执行：
– ROLLBACK;

SQL Server 数据库日志文件管理与收缩实践

发表于 2026-07-20 分类于 数据库

背景与问题

本文记录了一次针对数据库 XXX__Web 的日志维护操作，包括：

  • 将恢复模式临时切换为 简单模式（SIMPLE） 以收缩日志；
  • 使用 DBCC SHRINKFILE 收缩日志文件至指定大小；
  • 查询当前数据文件大小以验证效果；
  • 最后将恢复模式恢复为 完整模式（FULL） 以保证数据安全。

⚠️ 重要提示：在生产环境中操作前，请务必完整备份数据库，并确认业务允许短暂的日志截断操作。本文操作仅适用于测试或开发环境。

操作步骤详解

1. 查看当前数据库恢复模式与文件大小（操作前基准）

2. 将恢复模式切换为“简单模式”

简单模式下，SQL Server 会自动截断事务日志，释放日志文件中的空间（但物理文件大小不一定自动缩小）。

为什么要做这一步？
在完整恢复模式下，日志文件会持续记录所有事务，即使执行 SHRINKFILE 也可能因为日志尾部处于活动状态而无法收缩到目标大小。切换到简单模式后，检查点会截断非活动日志，释放空间，便于收缩。

3. 收缩日志文件到最小可能大小

参数表示将文件收缩到当前分配的已用空间大小，不移动任何数据，速度最快。

执行后，日志文件会缩小到尽可能小，但可能仍保留一些已分配但未使用的空间。

4. 收缩日志文件到指定大小（例如 100 MB）

有时我们希望将日志文件固定为某个较小尺寸（比如 100 MB），以便后续管理。使用带有目标大小的 SHRINKFILE：

这里的 100 单位是 MB，表示将日志文件收缩到 100 MB。

注意：如果当前日志中仍有活动事务（如未提交的长事务），收缩可能无法达到目标大小，需要等待事务完成或结合备份日志操作。

5. 验证收缩结果

6. 恢复为完整恢复模式（生产环境必做）

简单模式不支持点时间恢复（Point-in-Time Recovery），在测试完成后务必切换回完整模式，并立即执行一次完整备份，建立日志备份链。

注意事项与最佳实践

备份先行：任何 SHRINKFILE 操作前，务必执行完整数据库备份，避免意外数据丢失。

避免频繁收缩：频繁收缩日志会导致日志文件频繁增长，影响性能。建议定期维护，或设置合理的初始大小和自动增长增量。

监视活动事务：如果收缩无法达到目标大小，检查是否有未提交的事务或复制、镜像等功能正在使用日志。

测试环境验证：先在测试环境模拟操作，再应用于生产。

监控磁盘空间：收缩释放的空间可以用于其他用途，但也要注意数据库增长趋势，合理规划存储。

扩展知识：日志文件为什么会膨胀？

在 完整恢复模式 下，所有事务都写入日志，直到日志备份截断非活动部分。

如果长时间未进行日志备份，或存在未提交的长事务，日志会持续增长。

自动增长设置（如每次增长 10%）可能导致文件碎片化，影响 I/O 性能。

建议结合定期日志备份（如每小时一次）和监控报警，实现日志空间的主动管理。

结语

本文记录了一次完整的数据库日志维护操作，从切换模式、收缩、验证到恢复模式。掌握这些技能可以帮助测试人员高效管理测试数据库，避免磁盘空间告警，确保测试环境稳定运行。
